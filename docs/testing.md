# Testing

This document describes the test setup for the repository. Tests are run with **Vitest** via `pnpm test` (`vitest run`).

## Test runner

- Runner: [Vitest](https://vitest.dev) (`vitest@4`, dev dependency).
- Command: `pnpm test` → `vitest run` (single-shot, no watch).
- There is no separate vitest config file; tests are auto-discovered under `tests/`.
- `tests/` contains **28 test files** with **241 test cases** (`it(...)`).
- TypeScript tests are run directly via Vitest (esbuild transform); `tests/` and `tools/` are excluded from `tsconfig` (see [ci.md](./ci.md)).

## Test categories

### Offline unit tests (default)

Most tests run entirely in-memory using the fake repositories in [`tests/helpers/in-memory.ts`](../tests/helpers/in-memory.ts):

- `InMemoryBotRepository`, `InMemoryCredentialRepository`, `InMemoryRoomRepository`, `InMemoryRoomMemberRepository`, `InMemoryUsageRepository`, `InMemoryTenantRepository`, plus in-memory event/action/cooldown/rate-limit/dedup stores.
- These mirror the Mongo repository interfaces so services can be tested with identical dependency shapes.
- Notable difference: the in-memory bot repository defaults `triggerMode` to `'question'`, whereas production defaults to `'mention'` (see [limitations.md](./limitations.md) — the test fake intentionally uses a different default than the production code path).

Key offline test files:

- `tests/v1-api.test.ts` — HTTP surface via `createApp()`: route inventory, auth, response shapes, status codes.
- `tests/authorization.test.ts`, `tests/http-tenant-isolation.test.ts`, `tests/cross-tenant-security.test.ts` — tenant isolation and authorization behavior.
- `tests/ai.service.test.ts`, `tests/mention-detector.test.ts` — AI trigger/mention logic.
- `tests/automation.test.ts`, `tests/automation-pipeline.test.ts` — automation rules + pipeline wiring.
- `tests/bot-manager.test.ts` — boot, start/stop, timers, generation-based race handling.
- `tests/event-bus.test.ts`, `tests/durable-event-store.test.ts` — event bus + event store (the latter also has real-Mongo cases).
- `tests/message-dedup.test.ts`, `tests/moderation.test.ts` — dedup and moderation.
- `tests/credential-encryption.test.ts`, `tests/credential.service.test.ts` — credential lifecycle.
- `tests/environment.test.ts` — required env var validation.
- `tests/error-handler.test.ts` — error middleware behavior.
- `tests/worker.test.ts`, `tests/deployment-single-runtime.test.ts` — assert the worker is **not** started in production and the single-process runtime.
- `tests/api-key.test.ts`, `tests/dod-flow.test.ts`, `tests/room.service.test.ts`, `tests/usage.service.test.ts`, `tests/openai-reliability.test.ts`, `tests/v1-legacy-migration.test.ts`, `tests/bot.service.test.ts`, `tests/clubhouse-adapter.test.ts` — remaining unit coverage.

### Real-Mongo integration (mongo-ownership)

`tests/mongo-ownership.test.ts` verifies **server-side atomicity** of the event-store claim and the action-idempotency claim against a real MongoDB (in-memory stores cannot prove atomicity, so they are deliberately not used here).

The Mongo instance is provided by, in order of preference:

1. `MONGODB_TEST_URL` environment variable if set, or
2. a local `mongod` already listening on `127.0.0.1:27017`, or
3. a disposable `mongo:6` Docker container spawned for the run (`docker run`), cleaned up in `afterAll`.

All tests are scoped to the dedicated `clubhouse_ownership_test` database so they can never touch development data. Tests assert: claim ownership, stale-claim recovery, `markExecuted`/`markFailed` ownership guards, attempt limits, and lease expiry.

> Note: `mongo-ownership` tests require either `MONGODB_TEST_URL`, a running local `mongod`, or Docker. The rest of the suite does not require MongoDB.

## Test commands

| Command | Purpose |
|---|---|
| `pnpm test` | Run the full suite once (Vitest, non-watch) |
| `pnpm test <file>` | Run a single test file |

## Coverage

There is **no coverage configuration** and no coverage gate in CI. Do not assume coverage percentages — none are generated by tooling.
