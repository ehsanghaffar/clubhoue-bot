# Usage

This document describes usage telemetry as implemented in [`src/core/usage/`](../src/core/usage/) and the `UsageEvent` model ([`src/models/usageEvent.ts`](../src/models/usageEvent.ts)).

## Overview

`UsageEvent` is an **append-only** telemetry record. It is persisted to MongoDB for basic analytics. **Billing is intentionally not implemented** — the source comment states "Billing is intentionally not implemented yet", and there is no billing code anywhere in the repository.

## The `UsageEvent` Document

Stored in the `usageevents` collection.

| Field | Type | Notes |
|---|---|---|
| `_id` | `string` | `nanoid(12)` generated by default |
| `tenantId` | `string` | required, indexed |
| `botId` | `string` | required, indexed |
| `roomId` | `string?` | optional |
| `type` | `UsageType` | 8 types (below), required |
| `timestamp` | `Date` | default `Date.now` |
| `meta` | `Mixed` | optional extra data |
| `createdAt`, `updatedAt` | `Date` | Mongoose timestamps |

Index: `{ tenantId: 1, botId: 1, timestamp: -1 }`.

### Usage types

```ts
'message_received' | 'message_sent' | 'ai_request' | 'ai_response'
| 'speaker_invite' | 'room_join' | 'room_leave' | 'automation_triggered'
```

## What Is Recorded (and where)

Usage is recorded from two places:

1. **`UsageStage`** (the last event-pipeline stage, [usage-stage.ts](../src/core/usage/usage-stage.ts)) maps platform-observed community events onto the usage vocabulary:

   | Community event | Usage type |
   |---|---|
   | `room.joined` | `room_join` |
   | `room.left` | `room_leave` |
   | `message.created` | `message_received` |
   | `speaker.invited` | `speaker_invite` |

   Because the usage stage runs **last**, a message blocked by moderation never produces a usage record.

2. **Closer to the source**, inside the subsystems that emit them:

   - `ai_request` and `ai_response` — recorded by `AgentService` (`agent.service.ts`) around AI generation.
   - `automation_triggered` — recorded by `AutomationStage` when at least one rule produced a result, with `meta.ruleIds`.
   - `message_sent` — recorded by `room.service.ts` when the bot sends a message (outbound).

## Aggregation

- `UsageService` (`usage.service.ts`) delegates to `MongoUsageRepository` (`usage.repository.ts`).
- `summarizeByBotAndTenant` counts `message_received`, `ai_response`, `ai_request`, `speaker_invite`, `automation_triggered` for a bot and **hardcodes `users: 0` and `rooms: 0` and `errors: 0`** (the source comment explains that a distinct-user count derived from joins/leaves is not meaningful). This is a current limitation — see [limitations.md](./limitations.md) and the final report.
- `AnalyticsService.summarizeBot` (`analytics.service.ts`) composes the raw counters with real counts: `rooms` = number of `BotRoom` documents for the bot, `users` = `countDistinctUsers` across the bot's rooms. No time-series bucketing.

## What the API Exposes

Both handlers live in [`src/api/controllers/usage.controller.ts`](../src/api/controllers/usage.controller.ts) (there is **no separate events controller**):

- `GET /v1/bots/:botId/usage` → `{ data: UsageSummary }` from `AnalyticsService.summarizeBot`. Requires the bot to be found (else 404).
- `GET /v1/bots/:botId/events` → `{ data: UsageEvent[] }` from `usageService.listByBotAndTenant` (newest first). Optional `?limit` query — digits only, clamped to **1–200**, default **50**.

Both are tenant-scoped via the authorization middleware (a bot of another tenant is treated as 404 — see [security/authentication.md](./security/authentication.md)).

## Usage Summary Shape

```json
{
  "messages": 0,
  "aiResponses": 0,
  "aiRequests": 0,
  "users": 0,
  "rooms": 0,
  "speakerInvites": 0,
  "automationActions": 0,
  "errors": 0
}
```

(`users`/`rooms` are populated with real values by `AnalyticsService.summarizeBot`; the repository-level summary leaves them zero.)
